2 The User Interface

The main window is a fixed three-panel layout. Panels can be resized or hidden but the structure never changes. Everything lives in ContentView.swift.

Fig 1 — The three-panel main window. Left sidebar shows folder tree and smart filters. Center grid shows image thumbnails (blue outline = selected). Right inspector shows the selected image with its AI generation recipe.

4 Three-Speed Data Model

The app uses three layers of storage with very different access speeds. The right layer is chosen for each task automatically — this is what makes browsing feel instant even with large libraries.

Fig 3 — The three-speed data architecture. Green = instant RAM access. Amber = fast SQLite queries. Red = slow file reads (only during initial scan).

5 Core Data Types

Defined in Models.swift. These are the fundamental "blueprints" for data throughout the entire app.

Category
A folder — or a synthetic group like Favorites or Smart Filters.
id — unique identifier (path-based) folderURL — location on disk displayName — what appears in the sidebar images[] — array of ImageItems
ImageItem
One image file. The basic unit the grid works with.
id — unique identifier (file path) url — full path on disk displayLabel — filename for the grid creationDate — file creation date
ImageMetadata
The AI "recipe" embedded in an image — the prompt, settings, and parameters used to generate it.
prompt — what the user asked for negativePrompt — what to avoid generationParameters[] — model, seed, steps… textEntries[] — all other embedded text
SmartFilter
A saved, named search query that appears in the sidebar.
id — UUID name — display label query — search string scopeFolderURL? — optional folder scope
MetadataField
One metadata column. Used to populate the filter bar dropdowns.
.model — the AI model used .sampler — the sampler algorithm .scheduler — the scheduler .vae — the VAE model .upscaler — the upscaler used
MetadataFilter
"Show only images where Field = Value." Applied via the filter bar.
field — which MetadataField to filter on value — the exact value to match
Data flow from disk to screen:
File on disk → parsed by PNGInfoReader → ImageMetadata → stored in MetadataIndex as a row → queried back as ImageItem paths → wrapped in a Category → displayed by ContentView.

6.3 — Background Indexing

Runs automatically after any folder is opened. Happens entirely in the background — the UI stays fully responsive while it runs.
⚙️Background metadata scanLibraryStore › startBackgroundIndexing
LibraryStore.startBackgroundIndexing
  ├─ MetadataIndex.init                  ← Opens or creates the SQLite file on disk
  │     └─ createSchema                  ← Creates table + columns if not existing;
  │                                          migrates schema if new columns were added
  └─ MetadataIndex.scan                  ← Main indexing loop
        └─ (for each image file)
              ├─ fileModDate             ← Has this file changed since last scan?
              │     (unchanged → skip, changed/new → read it)
              └─ extractRow              ← Parse and normalize the image's metadata
                    ├─ PNGInfoReader.read / JpegMetadataReader.read
                    ├─ MetadataReader.readSidecar   ← check .txt sidecar file
                    ├─ normalizeModelName  ← strips hashes [abc123], -fp16 etc.
                    └─ splitA1111Sampler  ← splits "DPM++ 2M Karras" → sampler + scheduler
              └─ bind → SQL INSERT/UPDATE ← writes row to database
        └─ removePaths                   ← Deletes rows for files that no longer exist
        → [progress bar updates every 100 files]
  ├─ resolveSmartFilters                 ← Re-runs all saved searches against new data
  └─ rebuildCategories                   ← Updates UI (smart filter rows, etc.)

8 Design Principles

These are the architectural decisions that explain why the code is structured the way it is.

Principle 1

One source of truth

LibraryStore owns all data. ContentView only reads from it and sends user actions to it — the UI never modifies data directly. This prevents "split brain" where different parts of the UI show inconsistent state.

Principle 2

Reactive UI — no manual refresh

ContentView uses SwiftUI's observation system: it automatically redraws whenever any @Published property in LibraryStore changes. There is no "refresh" button or explicit update call anywhere in the codebase.

Principle 3

Background work never blocks the UI

Folder scanning, metadata indexing, searching, and image loading all run asynchronously. The app is always responsive. Progress indicators show when work is happening. Images appear from memory while SQLite is still being built in the background.

Principle 4

Three-speed data access

Instant (0ms) — in-memory lists for browsing.
Fast (<50ms) — SQLite for searching and filtering.
Slow (seconds) — reading image files from disk (only on first scan or when modified).

Principle 5

Graceful degradation

Every metadata reader has a fallback chain: embedded PNG data → sidecar .txt file → folder JSON/CFG → show nothing gracefully. If a ComfyUI workflow is too complex to parse, it is silently skipped rather than crashing or showing garbage.

Principle 6

Schema changes are self-healing

When a new column is added to the SQLite database, the app detects it at startup, adds the column, then zeros all mod_date values — forcing every image to be re-read and the new column populated automatically. No manual migration steps needed.

Principle 7

Keyboard navigation stays out of its own way

KeyHandlingView only intercepts keyboard events when no text field has focus. Arrow keys navigate images when you're browsing, but type normally when the cursor is in the search box.
